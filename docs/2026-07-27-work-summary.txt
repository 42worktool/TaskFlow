5. 초기 렌더링이 느린 문제 진단 및 수정 (2단계)
----------------------------------------------------------------
[1차: 인증 부트스트랩 요청 1회 축소]
- frontend/src/router/index.ts 의 전역 네비게이션 가드가 매 최초
  진입 시 initializeAuth() 를 기다리는데, 그 내부가
  POST /api/auth/refresh → GET /api/auth/me 를 순차 호출하고 있었음.
- 발견: backend rotateSession() 이 refresh 처리 중 이미
  prisma.user.findUnique 로 유저 정보를 가져오는데, 컨트롤러가
  access_token 만 응답하고 유저 정보를 버려서 프론트가 동일한 유저를
  /api/auth/me 로 또 조회하고 있었음 (완전 중복 DB 왕복).
- 조치:
  - backend/src/modules/auth/auth.service.ts: rotateSession() 이
    user 정보도 함께 반환하도록 변경.
  - backend/src/modules/auth/auth.controller.ts: refresh 응답에
    user 필드 포함 (login/signup과 동일한 응답 형태로 통일).
  - frontend/src/services/auth.ts: RefreshResponse에 user 필드 추가,
    requestRefresh()가 응답의 user로 authState.user를 바로 채움.
    이제 불필요해진 requestCurrentUser()(/api/auth/me 별도 호출)와
    중복 타입 AuthSessionResponse 제거.
  - 효과: 최초 진입 시 직렬 요청 3개(refresh, me, lists) → 2개
    (refresh, lists)로 축소.

[2차: 진짜 핵심 원인 — Redis 블로킹 명령이 전체 커넥션을 막고 있었음]
- 그래도 느리다는 피드백을 받고 실측(curl -w)해보니
  POST /api/auth/refresh 가 매번 정확히 약 3초 걸리는 것을 확인.
  (프론트 개선과 무관하게 백엔드 자체가 느렸음)
- backend/src/modules/auth/auth.service.ts의 rotateSession() 내부에
  console.time 계측을 임시로 넣어 확인한 결과, Redis 명령
  (getDel, sRem, createSession의 multi/exec) 각각이 순수 Redis
  레이턴시(<1ms, redis-cli --latency로 확인)와 무관하게 약 1초씩
  걸리고 있음을 확인.
- 원인: backend/src/lib/mail-queue.ts 의 메일 워커가
  redis.brPop(KEY, 1) (1초 타임아웃 블로킹 명령)을 무한 루프로
  호출하는데, 이때 앱 전체가 공유하는 싱글턴 Redis 커넥션
  (lib/redis.ts의 getRedisClient())을 그대로 사용하고 있었음.
  node-redis는 한 커넥션의 명령을 FIFO로 처리하므로, 다른 요청이
  보낸 Redis 명령이 진행 중인 BRPOP이 끝날 때까지(최대 1초) 대기해야
  했음. refresh 요청 하나가 Redis 명령을 3번 쓰다 보니 3초가 걸린 것.
- 조치: mail-queue.ts의 블로킹 폴링 루프가 redis.duplicate()로 만든
  전용 커넥션을 쓰도록 변경 (node-redis 공식 권장 패턴 — 블로킹
  명령은 항상 별도 커넥션에서 실행).
- 효과: POST /api/auth/refresh 응답 시간 3007ms → 5ms (약 600배
  개선). 계측용 console.time 코드는 확인 후 원복.
